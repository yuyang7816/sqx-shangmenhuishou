# 服务端功能说明

服务端没有给消费者点的页面。它是一直开着的程序：用户端、师傅端和管理端把「登录、预约下单、抢单、结算、保证金、提现、认证」这些请求发给它，它检查是否允许、把结果存进数据库，必要时再去问微信、支付宝、短信、对象存储这些外面的服务。

可以把它理解成总台。三个前台（用户端、师傅端、管理端）说的话，都由总台记账，并在需要时给外面的公司打电话。

数据库配置在 `shangmenhuishou-server/sqx-application/src/main/resources/application-dev.yml`（本地）和 `application-prod.yml`（线上）。库名默认 `smhs`，初始化脚本是 `shangmenhuishou-server/db/smhs.sql`。

启动类是 `com.sqx.SqxApplication`（模块 `sqx-application`）。端口是 **9692**，所有接口都在 `/sqx_fast` 下面。接口文档在：

http://127.0.0.1:9692/sqx_fast/doc.html

文档标题为「上门回收系统接口文档」，分组含：业务模块 - 管理端（`/admin/**`）、业务模块 - APP 端（`/app/**`）、系统模块等。

Redis 写在配置里（`redisson`，地址本机 `6379`）。当前 `sqx.redis.open` 和 `sqx.shiro.redis` 都是关的，所以它不是必须先启动的服务。如果以后把开关打开，就要先启动 Redis。

核心业务代码在 `sqx-modules/sqx-app`，包名 `com.sqx.app`。

## 它为消费者（用户端）做的事

这些都是用户在手机里点一下之后，由服务端完成的：

- **注册和登录**：检查手机号和短信验证码，或检查密码；也支持微信小程序登录等。通过后发给用户一张登录凭证（JWT，请求头名是 `token`）。之后需要登录的接口都要带这张凭证（见 `AppAuthController`、`AppUserController`、`VerifyCodeController`）。
- **首页内容**：返回轮播图、废品分类、回收项目与价格等，供用户浏览与选品。
- **地址管理**：新增、修改、删除、列表上门地址（`AppAddressController`）。
- **预约下单**：按回收项目创建订单（`/app/waste/order/itemOrder`、`save`），状态进入「待接单」。
- **订单查询与取消**：我的订单统计、订单列表 / 详情、用户取消订单。
- **邀请好友**：邀请关系与分销相关能力（含提现账号 / 提现记录等 referral 模块）。
- **招募入口**：用户端可进入招募回收员相关页面，提交后由后台审核。
- **消息、帮助、协议、反馈、注销**：把后台维护的内容发给用户端，或记下注销申请。

## 它为回收员（师傅端）做的事

- **接单池**：按城市查看待接单订单（`/app/waste/order/pool`）。
- **抢单 / 接单**：接单后订单进入「待服务」（`/app/waste/order/take`）。
- **履约**：开始服务 → 进行中；完成订单 → 已完成；也可停止服务回到接单池，或回收员取消订单。
- **实名认证**：提交个人认证资料（`AppUserAuthenticationController`）。
- **保证金**：缴纳与保证金记录（`AppDepositRecordController`），支付走微信 / 支付宝回调后入账。
- **钱包与提现**：余额、明细、提现申请与收款账号绑定。提现只生成待审核记录，不会在这一步自动把钱转到对方支付宝或微信。
- **消息、帮助、设置与注销**：同用户端一类站内能力。

## 它为管理端做的事

- 工作人员登录（验证码 + 密码），并按角色限制能看的菜单。验证码也由它生成。
- 提供运营数据概览要用的统计数字（`AdminIndexController`）。
- 维护废品分类、回收项目、价格、订单、师傅、认证 / 招募审核、财务、轮播与首页装修、帮助文章、反馈、系统配置等。
- 订单、提现、保证金、认证一类审核按钮会改业务状态。涉及原路退款或支付回调时，支付密钥必须有效。
- 管理员、角色、菜单、字典、系统配置（`sqx-modules/sqx-system`）。

## 订单状态机

定义在 `com.sqx.app.waste.order.order.enums.OrderStatus`：

| 状态码 | 含义 | 说明 |
|---|---|---|
| 0 | 待接单 | 用户已下单，等待回收员抢单 |
| 1 | 待服务 | 已被接单，等待开始服务 |
| 2 | 进行中 | 回收员已开始上门服务 |
| 3 | 已完成 | 服务完成（业务侧多为线下结算） |
| 4 | 已取消 | 用户或回收员取消 |

典型流转：

1. 用户选分类 / 项目 → 填地址与预约时间 → 下单（待接单）。
2. 师傅在接单池抢单（待服务）。
3. 师傅开始服务（进行中）。
4. 师傅完成订单（已完成）；过程中用户或师傅可取消（已取消）；师傅也可停止服务使订单回到接单池。

## 对接了哪些外面的服务

下面每一项都是服务端真的会向外发送请求的。密钥没填时，它不会假装成功，前台会看到失败提示。

密钥主要在管理端「系统配置」中维护，改完保存后，下次请求才会用新值。

### 短信

注册、验证码登录、找回密码，都由服务端发短信。可以切换服务商。只把程序跑起来，不会自动拥有短信额度。

### 微信支付 / 支付宝

保证金缴纳等场景会走支付下单与回调（`WxPayController`、`AlipayController`）。需要商户号 / 应用编号和密钥。回收主流程本身多为线下结算，不强制用户在线支付废品货款。

### 图片存储

用户和管理端上传的图片由服务端接收（`FileController`）。可对接阿里云 OSS 等，也可按配置走本地存储。没配好时，上传接口会失败。

### 地图

地址选点、经纬度相关能力会用到地图密钥（`MapController`）。密钥要自己申请。

## 这些不是外面的公司

- **订单状态流转、接单池、线下结算记账**：只改自己的数据库。
- **提现**：只保存收款账号和金额，等管理端审核。
- **邀请分成规则**：在自己的数据库里计算。
- **站内消息、帮助文章、协议、轮播**：读自己的库。
- **操作日志、权限、角色**：只约束管理端工作人员。

## 三个前台怎样和它配合

用户端、师傅端和管理端都不直接保存订单核心数据。它们把请求发给服务端，服务端再决定要不要去问微信、短信或图床。

所以：

- 服务端没启动时，三个前端都能打开界面，但登录、列表、下单、抢单都会失败。
- 外面的密钥只配在服务端能读到的「系统配置」里。只在 App 页面上改文字，不会变成已经开通了微信支付。
- 管理端改完分类、价格、轮播、帮助并保存后，用户端 / 师傅端下次打开才会看到新内容。
- 要测完整回收链路：管理端维护分类与项目 → 用户端下单 → 师傅端抢单并完成。
